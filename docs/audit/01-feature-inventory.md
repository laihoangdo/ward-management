## Authentication / authorization details

AUTH-001 purpose: establish server identity before sensitive data access. UI `/sign-in`, dashboard LoginScreen; backend `/oauth2/authorization/oidc`, `/api/account`, `/api/authenticate`, `/api/auth-info`; Keycloak and local user synchronization. Success: real IdP login returns to dashboard with active profile. Failures: unavailable issuer/backend, inactive/locked profile, unmapped roles, missing policy. AUTH-002 calls POST `/api/logout` and follows logoutUrl; verify both backend and IdP session termination. Browser round trips remain unverified; code confidence high, business-policy confidence medium.

RBAC-001..004 use `rbac_profile`, assignments, record scopes, settings and audit tables from the RBAC changelog. Service AOP is dynamically applied: absence of controller annotations is not proof of unrestricted writes. Success must include scoped list/count/detail/export, controlled delegation, and live revocation. Negative cases: cross-territory IDs, street/alley reassignment, grant escalation, locked users, policy changes, identity-provider failure. RbacServiceTest passed as part of 107 Java tests; no browser or full integration proof. Default menus are merged into server menus by App: confirm whether an omitted menu should remain disabled.

## Records and integrity

HH-001..003: `Household` requires code (unique), houseNumber, street, hamlet, ownerName, ownerPhone, and facility type. It relates to `Resident` and `AreaZone`. Success means create/edit survives reload and corresponding roster/counts remain correct. householdApiService makes multiple household/resident requests and catches several errors; incomplete roster synchronization is a confirmed code-level risk, not an executed defect. Deletion separately deletes resident rows and household. Negative cases include duplicates, missing fields, network failure mid-operation, forbidden coordinate edits, scope changes, and unauthorized deletion.

RES-001: `Resident` links to Household; CRUD and residence-category filters exist. Check residence enum translation, resident identity protection, household reassignment, null/invalid inputs and data integrity. Existing type errors include obsolete field names and translated enum values in duplicate screens. Neither aggregate demographic correctness nor independent resident workflows are runtime proven.

DOC-001: DocumentRecord CRUD and date-based UI status/renewal; verify valid/expired/near-expiry boundaries and persisted expiry after reload. DOC-002 stores a pending reminder request; no worker/provider delivery was confirmed. Success criteria must distinguish queued request from delivered notification. AREA-001 groups households and manages zone metadata; boundary geometry and assignment semantics need business confirmation. ALERT-001 operational `security_alert` records differ from RBAC `settings/alerts`; confirm unified UI meaning.

LOG-001: service aspect sets server identity/time and rejects edits/deletes even though generated REST/UI exposes them. That is a UI/API inconsistency requiring explicit user feedback and tests. `householdApiService` contains synthetic SHA256-like integrity display fallbacks; no cryptographic integrity claim is verified. Test append-only behavior, record scope, identity forgery, and failure atomicity.

## GIS / capture / preferences / operations

GIS-001..005 use scoped operational records, static GIS JSON/TypeScript datasets, external tiles and a copied GLB. Success requires meaningful feature selection, correct household linkage, visible layers and persisted authorized edits, not only a canvas. Verify blank/failed tiles, invalid coordinates, no WebGL, mobile layouts, screenshot download, and permissions. Building settings have server-backed MapLibre behavior and localStorage-backed spatial behavior; cross-view persistence is ambiguous. API validation requires name <=120 chars, height 2..300, six-digit hex color and floorCount 1..100. Provider API key ownership/restrictions remain unresolved.

CAP-001 uses getUserMedia and local English/Vietnamese Tesseract assets; OCR results are editable and used for resident updates. Photos and local caches use browser storage. Test denied camera access, unsupported devices, cancellation, malformed/large files, OCR errors, user correction, storage limits, and encryption/masking. No proof of server photo persistence or multi-device access. CAP-002 requires browser speech API support; test unsupported/denied microphone and applying transcript to actual results. PREF-001 saves profile locally; sound and refresh settings begin as UI state, so durable operational effects are not established.

OPS-001 includes generated CRUD for six domain entities, user/authority administration endpoints, health, metrics, logs, configuration and docs. Public health/info/prometheus matchers exist; deployment exposure and desired access require confirmation. JUnit IT tests exist but were not executed. Build scripts support Jib/JAR/WAR and Docker; deployment compatibility is unverified.
